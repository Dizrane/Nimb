# DNS и производительность — 20 ноября 2026

Устранена программная задержка: ожидание неотвечающего DNS задерживало HTTPS-проверку остальных провайдеров. Все приведённые ниже сетевые замеры выполнены с включённым сторонним VPN. Они позволяют сравнить скорость двух версий кода в одинаковых условиях, но не показывают работоспособность DNS без VPN и не устанавливают причину отказов, которые пользователь наблюдает без него. Адреса провайдеров, повторные попытки, проверка сертификатов и правила оценки доступности сохранены.

На macOS в каждом прогоне сохранились все 188 результатов: GeoHide EU — 74, MagicDNS — 12 неудачных разрешений имён, malw.link — 14, GeoHide RU и US — по 44. ## Что замедляло приложение и что изменено

1. **Общий барьер между DNS и HTTPS.** Сначала приложение ожидало завершения всех DNS-запросов, включая два молчащих адреса MagicDNS с повторными попытками. На macOS только этот этап занимал около 8 секунд. Теперь HTTPS-запросы к уже найденным адресам идут одновременно с оставшимися DNS-запросами. Неотвечающий провайдер по-прежнему проверяется полностью, но остальные работают в это время.
2. **Общая очередь Windows на 24 операции.** Медленный провайдер занимал места, предназначенные также для остальных. Теперь у каждого провайдера собственные 16 HTTPS-работников; разрешение имён тоже ограничено отдельно для каждого. Лимит HTTPS соответствует macOS. Сбор результатов сохраняет порядок провайдеров, целей и адресов.
3. **Повторное чтение одних сетевых настроек macOS.** После получения конфигурации поиск частичного включения заново запускал `networksetup` для каждого провайдера и каждого подключения. Проверка прежних адресов тоже читала настройки повторно. Теперь обе используют уже полученный снимок. Даже при отдельном вызове поиск частичного включения читает каждое подключение один раз.
4. **Накладывающиеся опросы интерфейса Windows.** Обычный таймер, получение фокуса и частый опрос во время операций могли одновременно вызывать `GetState`. Теперь они разделяют один незавершённый запрос: очередь опросов не накапливается, ответы не меняют состояние в обратном порядке.
5. **Ожидание процессов macOS.** В DNS-проверке ожидание завершения `dig`/`curl` переведено с `waitUntilExit` на сигнал завершения процесса, как уже сделано в других частях проекта.
6. **Время жизни Swift-замыканий.** Повторный прогон регрессионных тестов воспроизвёл аварийное завершение внутри `withoutActuallyEscaping`. Рабочий блок Dispatch мог ещё удерживать замыкание после `DispatchGroup.leave()`, когда ожидающий поток уже продолжил выполнение. Убрано неверное утверждение о времени жизни: передаваемая в очередь работа теперь явно `@escaping`.

Повторы, добавленные 14 ноября для устойчивости диагностики, сохранены. Не возвращено прежнее ошибочное правило, при котором один неудачный запрос объявлял IP недоступным сразу для всех доменов. Защита MOD и запрет отправки отчётов из изменённой сборки не менялись.

**MagicDNS.** Обе текущие записи не дали ни одного ответа в отдельной серии; штатная проверка также не получила адресов для всех 12 целей на macOS и Windows. [Официальная страница](https://magicdns.ru/) на момент проверки показывает «Калибровка шлюзов» и «СКОРО» вместо основных и резервных IP. По этим ответам через VPN нельзя установить причину недоступности адресов при прямом подключении. Новая подтверждённая пара не опубликована в проверенной инструкции, поэтому адреса не заменены догадками. Провайдер не удалён из приложения.

**malw.link.** Основной адрес прошёл серию полностью, резервный пропустил по одному запросу UDP и TCP. Повтор и второй сервер остаются необходимыми. По трём попыткам нельзя определить, связан ли пропуск с сервером, маршрутом или текущим туннелем.

**GeoHide.** UDP-запросы прошли на всех текущих адресах. Российский резервный адрес не ответил через TCP, хотя UDP работал. Это различие протоколов стоит учитывать при разборе сети; оно не означает полный отказ этого DNS. [Официальная страница состояния](https://status.dns.geohide.ru/ru) показывает узлы EU/US в сети, но внешний мониторинг не гарантирует доступность от конкретного оператора.

**Gemini.** Сайт не прошёл проверку ни у одного отвечающего провайдера. В большинстве запросов он перенаправлял на Google `/sorry`; в части Windows-запросов ответа не было. API при этом обычно отвечал. Перенаправление `/sorry` — ответ Google с проверкой/ограничением, а не доказательство отключения DNS. У остальных пяти сервисов проверяемые сайт и API прошли пороги. Ответ без входа в аккаунт не подтверждает генерацию, авторизацию и работу подписки.

## Можно ли утверждать, что усилились блокировки

Пока нет достаточных данных для такого вывода. Во время измерений основной интерфейс интернета на Mac — `utun4`; сторонний туннель не отключался, Windows использовала общую сеть Parallels. Пользователь подтвердил, что замечает проблемы также без стороннего VPN, однако серия прямых измерений без него в этой работе не проводилась.

Отказ MagicDNS и отдельные потери malw.link подтверждены из текущего соединения. Они не доказывают общую недоступность этих серверов во всём интернете и не позволяют отделить блокировку оператором от проблемы провайдера. При блокировке самого HTTPS/SNI смена DNS может оказаться недостаточной; такое ограничение описано и в [документации malw.link](https://github.com/ImMALWARE/dns.malw.link).

По этой серии через VPN нельзя рекомендовать провайдера для подключения без VPN. Для такого выбора требуется отдельный прямой прогон; официальная страница провайдера и его внешний мониторинг также не заменяют проверку от конкретного оператора.
